# salon-analytics
팀원: 위지현 마케팅(인스타, 당근마켓), 신인희  마케팅(샤오홍슈, 네이버), 손기승(데이터 분석, 챗봇), 신혜윤(보고서)
## 프로젝트 소개

서울의 소상공인 점포와 청년팀이 1:1로 약 3개월(12주) 동안 협업하는 프로젝트로 청년팀은 마케팅 2명 AI 데이터 분석 2명 총 4명이 한 팀으로 서울에 실제 영업하는 미용실 한 곳을 맡았다.
점포 데이터를 분석하고 AI와 디지털 마케팅을 활용해 매출·운영을 개선할 방향을 찾는 것을 목표로 한다.
우리 팀은 미용실의 재방문·취소·신규 유입·상담과 예약 전환 문제를 분석했고 점포와 함께 마케팅·운영 개선 방향을 정했다.
이 저장소는 그중 데이터 분석 부분이다.

## 사용한 데이터

| 데이터 | 내용 | 한 행의 단위 | 기간 |
|---|---|---|---|
| 매장 POS(핸즈) 예약상세 | 매장이 관리하는 방문·시술 기록 | 방문 한 건 | 2025년 1월~2026년 8월 |
| 네이버 예약자관리 내보내기 | 예약, 옵션(메뉴), 결제 금액, 요청사항, 취소 사유 | 예약 한 건·옵션 라인 | 2025-01-01~2026-08-23 |
| 네이버 예약 월별 리포트 | 신청·완료·취소·매출 | 월 × 상품구분 | 2025년 4월~2026년 8월 |

원본은 총 7개 파일이며 엑셀 통합문서와 `.xls` 확장자의 HTML 표로 구성된다. 세 자료를 합쳐 예약과 방문을 연결하고, 월별 집계로 정합성을 확인했다.
날씨 분석에는 같은 기간의 기상청 서울 일자료, 결제 시각 비교에는 2025년 7월과 12월 두 달의 카드매출 보조 자료를 사용했다. 월별 리포트 원본과 집계표는 공개 데이터에 포함하지 않는다.

## 데이터 합치기와 전처리

1. 네이버 예약 내보내기를 합치고 겹치는 예약은 최신 내보내기 기준으로 중복을 제거한다.
2. 메뉴별 옵션 라인을 예약 한 건으로 모아 라인 금액 합과 실결제 금액을 구분한다.
3. POS 방문을 정리하고 이용 일시·담당자·금액으로 예약 후보를 찾는다. 이름의 마스킹 형태도 대조하며, 이름 근거가 부족한 다중 후보 연결은 따로 표시한다.
4. 이름 첫 글자와 전화 뒤 4자리로 고객 키를 만들어 재방문을 계산한다. 동명이인·키 충돌과 관측 기간 밖 방문은 한계로 남는다.
5. 메뉴 94종을 시술 카테고리로 묶고 네이버 자동번역 외국어 표기를 한국어 메뉴와 대응시킨다.
6. 월별 리포트에서 겹치는 달과 상품구분을 정리한다.
7. `build.py`의 assert 65개로 건수·금액 합·연결 결과를 확인한다. 기대값과 다르면 중단한다. 조건은 [pipeline_contract.md](pipeline_contract.md)에 정리했다.

## 공개한 데이터에 대해

현재 영업 중인 가게의 실데이터이므로 원본 엑셀·HTML과 정제 직후 데이터는 그대로 올리지 않았다.
공개한 `data/`는 원본을 합치고 정제한 뒤 사람과 가게를 알아볼 수 있는 칸을 가명·합성 값·기호로 바꾸고, 공개할 필요 없는 열을 뺀 것이다.

| 항목 | 공개 방식 |
|---|---|
| 고객 이름 | 일관된 가명 |
| 전화 | 전화번호 열 제거, 고객 키에는 합성 숫자로 바꾼 뒤 4자리만 유지 |
| 예약번호 | 일련번호 |
| 디자이너·상호 등 | 공개용 라벨 |
| 요청사항·취소 사유·직원 메모 | 허용 어휘 밖의 텍스트를 기호로 가림 |

원본과 같은 행·열로 대조할 수 있는 공개 표의 칸 중 약 **17.3%**가 바뀌었다. 가명·합성 값·기호·표시 라벨로 바뀐 칸을 세었으며, 뺀 열과 원본에 없는 표시용 `menu_ko` 열은 분모에서 제외했다. 결측끼리는 같은 값으로 셌다.

금액·일시·상태·건수 등 분석 값은 점포 동의를 받아 원본 그대로 두었다. `check_public_data.py`로 공개 데이터의 금액 합이 `build.py` 기대값과 원 단위로 일치하는지 확인할 수 있다.
노트북은 원본 분석과 같은 분석 코드를 공개 데이터로 다시 실행했고, 이름·라벨·외국어 메뉴 표시와 공개본 설명을 정리했다.
원본 분석과 숫자가 다른 곳은 열 수를 표시하는 줄, 03 ②-c2의 가린 텍스트 빈도표, 03 ②-a3 목록에서 전화 숫자를 가린 한 줄, 그리고 개발용 확인 출력(라이브러리 버전·폰트 점검)을 지운 셀 8개(노트북마다 2개)다. 자세한 범위와 차이는 [data/README.md](data/README.md)를 참고한다.

## 재현 방법

공개 노트북 실행에 사용한 Python은 3.13.9다. 이 저장소를 clone한 뒤 루트에서 설치한다.

```bash
git clone <이 저장소의 URL>
cd salon-analytics
python -m pip install -r requirements.txt
```

Jupyter 또는 VS Code의 노트북 환경에서 위 Python 환경을 커널로 선택하고, 작업 폴더를 `notebooks/`로 두어 01 → 02 → 03 → 04 순서로 실행한다. 별도 환경변수 없이 포함된 `data/`를 읽는다. 실행기는 별도로 준비하며 한글 폰트가 필요하다. Windows에서는 맑은 고딕 등을 사용할 수 있다. 폰트가 없으면 노트북이 나눔고딕 설치를 시도한다.

검증은 저장소 루트에서 실행한다.

```bash
python check_public_data.py
python check_public_data.py --selftest
```

공개 데이터로 확인할 수 있는 계약 32개와 단가표를 검사하며, 자기검사는 메모리 사본의 결제액을 바꿔 검증 실패가 감지되는지 확인한다.
`build.py`와 `check_hands.py`는 공개하지 않은 원본 입력이 있어야 실행된다. 원본을 보유한 경우에만 `requirements-build.txt`를 추가 설치한다.

## 알려진 한계

- 02의 이벤트 메뉴 판정은 중국어 자동번역 일부 표기를 놓친다. 완료 라인 기준 이벤트 비중 영향은 약 0.02%p다.
- 무료 부가 서비스로 분류된 계열에 단가 58,000원인 옵션 라인이 모든 예약 상태를 합쳐 7줄 있고, 그중 완료 예약의 라인은 4줄이다. 분류와 라인 단가가 완전히 일치하지 않는다.
- 고객 텍스트는 읽기 어렵고 일부 일반어까지 가려졌다. 텍스트 빈도표는 원본과 다르다.
- 고객 키는 고객 식별의 대리값이다. 데이터 시작 이전의 방문은 모르며 재방문에는 분할 시술이 섞일 수 있다.
- 관측 소요시간은 당일 정산된 표본에 한정된다. 운영 여유와 잠재 규모는 실제 추가 예약·매출 성과가 아니다.
- 전체 계약 65개 중 공개 데이터로 확인하는 것은 32개다. 원본 병합·월별 리포트·POS 조인은 이 검증만으로 재현할 수 없다.
